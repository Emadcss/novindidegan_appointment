# مستند پروژه

## سامانه کیوسک نوبت‌دهی کلینیک فوق تخصصی نوین دیدگان

**وضعیت سند:** نسخه جاری پروژه
**تاریخ:** ۱۴۰۵/۰۷/۰۷
**نوع سامانه:** کیوسک نوبت‌دهی حضوری + پنل مدیریت
**محیط اجرا:** Local / داخل کلینیک
**رابط کاربری:** Touch First
**فریم‌ورک:** Next.js + TypeScript
**UI:** Tailwind CSS v4

---

# 1. هدف و علت ساخت پروژه

این پروژه با هدف ایجاد یک **سامانه مستقل، سریع و ساده برای مدیریت نوبت مراجعین در داخل کلینیک نوین دیدگان** طراحی شده است.

سامانه قرار نیست جایگزین سیستم اصلی اطلاعات بیماران یا سیستم‌های مدیریتی مرکز شود.

وظیفه اصلی آن:

* کاهش ازدحام و فشار روی پذیرش
* ایجاد نظم در صف مراجعه‌کنندگان
* صدور شماره نوبت
* هدایت بیمار در فرآیند دریافت نوبت
* چاپ قبض نوبت
* مدیریت نوبت‌های روز جاری
* کنترل برنامه حضور پزشکان
* امکان استفاده همزمان از چند کیوسک

است.

سیستم به‌صورت **Local و مستقل از سیستم‌های اصلی کلینیک** طراحی می‌شود و کاربران عادی فقط از طریق کیوسک‌های مستقر در مرکز به آن دسترسی دارند.

پنل مدیریت نیز برای کارکنان مجاز مرکز در نظر گرفته شده است.

# 2. ویژگی مهم معماری پروژه

این پروژه یک سیستم عمومی اینترنتی نیست.

ساختار کلی:

```text
                 ┌──────────────────────┐
                 │   پنل مدیریت مرکز    │
                 │       Admin          │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │   Backend / Database │
                 └──────────┬───────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
        ┌─────────┐    ┌─────────┐    ┌─────────┐
        │ Kiosk 1 │    │ Kiosk 2 │    │ Kiosk 3 │
        └─────────┘    └─────────┘    └─────────┘
```

تمام کیوسک‌ها باید از یک منبع داده مشترک استفاده کنند.

بنابراین شماره نوبت نباید در خود Frontend تولید شود.

تولید شماره نوبت باید در Backend و Database انجام شود تا در صورت ثبت همزمان دو درخواست، شماره تکراری ایجاد نشود.

# 13. برنامه حضور پزشکان

یکی از تصمیم‌های مهم پروژه این است که برنامه پزشک فقط یک مقدار ساده مانند:

```text
active = true
```

نباشد.

برای هر پزشک باید امکان تعریف موارد زیر وجود داشته باشد:

* روزهای حضور
* ساعت شروع
* ساعت پایان
* فعال/غیرفعال بودن برنامه

مثلاً:

```text
دکتر A

شنبه:
10:00 → 14:00

دوشنبه:
16:00 → 20:00
```

در نتیجه اگر پزشک شنبه از ساعت ۱۰ فعال است، ساعت ۹:۳۰ امکان ثبت نوبت برای او وجود ندارد.

---

# 14. تغییرات اضطراری برنامه پزشک

پنل Admin باید بتواند برنامه را Override کند.

مثلاً:

```text
دکتر A
شنبه ۱۴۰۵/۰۷/۰۷
حضور: لغو شد
علت: فورس ماژور
```

یا:

```text
ساعت حضور:
10:00 → 12:00
```

این تغییر باید **سریعاً روی کیوسک‌ها اعمال شود**.

بنابراین Frontend نباید برنامه پزشک را برای مدت طولانی Cache کند.

منبع حقیقت:

```text
Database / Backend
```

است.

# 15. شماره نوبت

شماره نوبت به‌صورت Global نیست.

هر تخصص صف مستقل خودش را دارد.

مثلاً:

```text
جراحی قرنیه
1
2
3
```

و:

```text
اپتومتری
1
2
3
```

بنابراین گرفتن نوبت شماره ۱ در جراحی قرنیه باعث نمی‌شود اولین بیمار اپتومتری شماره ۲ بگیرد.

# 16. شناسه یکتا برای نوبت

منطق شناسایی نوبت بر اساس ترکیب زیر طراحی شده است:

```text

+
doctorId
+

+
```

یعنی:

# 17. جلوگیری از Race Condition

چون ممکن است چند کیوسک به‌صورت همزمان درخواست ثبت نوبت ارسال کنند، تولید شماره نوبت نباید به این شکل باشد:

```text
SELECT MAX(number)
+
1
```

به‌صورت ساده.

چنین روشی می‌تواند باعث شود:

```text
Kiosk 1 → شماره 12
Kiosk 2 → شماره 12
```

تولید شود.

راهکار صحیح باید در Backend/Database با Transaction و مکانیزم Atomic/Unique انجام شود.

Database باید آخرین مرجع اعتبار شماره نوبت باشد.

اما چون این پروژه عمداً از سیستم اصلی بیمارستان/کلینیک جداست، نباید این وابستگی باعث پیچیده شدن کیوسک شود.

# 25. سؤال سابقه جراحی

این سؤال نباید برای همه پزشکان اجباری باشد.

برای هر پزشک در پنل Admin یک گزینه وجود خواهد داشت:

```text
requiresSurgeryHistory
```

مثلاً:

```text
دکتر A
requiresSurgeryHistory = true
```

در این حالت سؤال:

> آیا سابقه جراحی در این مرکز را داشته‌اید؟

نمایش داده می‌شود.

اما:

```text
دکتر B
requiresSurgeryHistory = false
```

در این حالت سؤال نمایش داده نمی‌شود و Flow مستقیماً ادامه پیدا می‌کند.

بنابراین تصمیم‌گیری درباره این سؤال متعلق به **تنظیمات پزشک** است، نه Frontend.

# 32. امنیت اطلاعات

امنیت از همین مرحله باید در طراحی لحاظ شود، اما پیاده‌سازی کامل آن در Backend انجام خواهد شد.

اصول مهم:

### Frontend نباید به Database دسترسی مستقیم داشته باشد.

```text
Kiosk
  ↓
API
  ↓
Backend
  ↓
Database
```

### Validation باید دوباره در Backend انجام شود.

حتی اگر Frontend کد ملی را معتبر تشخیص دهد، Backend باید دوباره آن را بررسی کند.

### اطلاعات حساس نباید در Logهای عمومی ثبت شوند.

خصوصاً:

```text
nationalId
mobile
```

### API باید حداقل داده مورد نیاز را دریافت کند.

### دسترسی Admin باید Authentication/Authorization داشته باشد.

### عملیات ایجاد نوبت باید Transaction-safe باشد.

### اطلاعات نباید در URL قرار بگیرند.

```text
وضعیت فعال
روزهای حضور
ساعات حضور
نیاز به پرسش سابقه جراحی
```

قابل تنظیم خواهد بود.

# 35. برنامه استثنایی پزشک

برای مواردی مانند:

* مرخصی
* بیماری
* فورس ماژور
* تغییر ساعت
* تعطیلی
* جابه‌جایی برنامه

باید Override روزانه وجود داشته باشد.

برای مثال:

```text
Doctor: A
Date: 1405/07/10

Regular:
10:00 - 14:00

Override:
Disabled
```

یا:

```text
Override:
12:00 - 16:00
```

# 36. منطق فعال بودن پزشک

```text
Doctor Active?
        ↓
Specialty Active?
        ↓
Today is working day?
        ↓
Is there an override?
        ↓
Current time is within schedule?
        ↓
Can accept appointment?
```

بنابراین صرفاً فعال بودن پزشک کافی نیست.

# 37. زمان ثبت نوبت

Backend باید هنگام ثبت نوبت مجدداً بررسی کند:

```text
آیا پزشک فعال است؟
آیا تخصص فعال است؟
آیا امروز روز حضور پزشک است؟
آیا ساعت فعلی در بازه مجاز است؟
آیا برنامه اضطراری وجود دارد؟
```

این بررسی نباید فقط در Frontend انجام شود.

زیرا ممکن است در فاصله نمایش پزشک تا ثبت نهایی، Admin برنامه او را تغییر دهد.

# 40. تست چند کیوسک

یکی از مهم‌ترین مراحل تست:

```text
Kiosk 1 ─┐
         ├──> ثبت همزمان ──> Backend
Kiosk 2 ─┘
```

باید آزمایش شود که:

```text
Request A → شماره 1
Request B → شماره 2
```

و هرگز:

```text
Request A → شماره 1
Request B → شماره 1
```

اتفاق نیفتد.

این تست باید مستقیماً روی Database واقعی انجام شود.

---

# 41. تست تغییر برنامه پزشک

سناریو:

```text
10:00 پزشک فعال است
```

کاربر در کیوسک پزشک را مشاهده می‌کند.

سپس Admin در ساعت 10:01 پزشک را غیرفعال می‌کند.

اگر کاربر هنوز در Flow باشد و بخواهد نوبت را ثبت کند:

```text
Backend
   ↓
Schedule دوباره بررسی می‌شود
   ↓
ثبت نوبت رد می‌شود
```

و UI باید پیام مناسب نمایش دهد.

# 42. اصل مهم معماری

یکی از اصول اصلی پروژه:

> Frontend تصمیم‌گیرنده نهایی نیست.

Frontend فقط وضعیت فعلی را نمایش می‌دهد.

تصمیم نهایی درباره:

* پزشک فعال
* زمان حضور
* ظرفیت
* شماره نوبت
* اعتبار نوبت
* ایجاد نوبت

در Backend/Database انجام می‌شود.

# 45. وضعیت فعلی معماری

در این نقطه پروژه از یک Prototype ساده UI عبور کرده و به یک **سامانه واقعی Kiosk + Backend + Admin** تبدیل شده است.

مهم‌ترین تصمیمات معماری که نباید در ادامه تغییر کنند:

1. سیستم Local و مستقل از سیستم اصلی مرکز است.
2. نام و نام خانوادگی بیمار در کیوسک دریافت نمی‌شود.
3. اطلاعات تخصص و پزشک از Database می‌آید.
4. شماره نوبت برای هر تخصص مستقل است.
5. شماره نوبت توسط Backend/Database تولید می‌شود.
6. چند کیوسک باید همزمان قابل استفاده باشند.
7. برنامه حضور پزشک داده‌ای قابل مدیریت توسط Admin است.
8. Override برنامه باید بدون نیاز به تغییر کد اعمال شود.
9. سؤال سابقه جراحی وابسته به تنظیمات پزشک است.
10. اطلاعات حساس نباید در Frontend یا Logهای غیرضروری افشا شوند.
11. تمام مراحل غیر از Welcome و Printing قابلیت Back/Cancel دارند.
12. Session در صورت ۹۰ ثانیه عدم فعالیت Reset می‌شود.
13. UI کاملاً Touch Friendly است.
14. Timeline باید وضعیت فعلی فرآیند را به کاربر نشان دهد.
15. Backend مرجع نهایی صحت عملیات است.
